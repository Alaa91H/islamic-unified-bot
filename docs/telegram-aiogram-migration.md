# مسار نقل Telegram إلى aiogram

Pyrogram يبقى محصورًا مؤقتًا في المعالجات والبث التي لم تُنقل بعد. لا تُضف أي خدمة جديدة مرتبطة مباشرة بعميل Pyrogram؛ استخدم عقدًا من `bot.transport` بدلًا منه. يتضمن المشروع الآن محولي `PyrogramMessageTransport` و`AiogramMessageTransport` بعقد النص نفسه، ولذلك يمكن نقل المرسِل من دون تعديل منطق الأعمال.

## مراحل النقل

| المرحلة | ما ينقل | شرط القبول | التراجع |
|---|---|---|---|
| 1 | الإرسال النصي للخدمات | اختبارات العقد تمر على المحولين | إعادة حقن محول Pyrogram في الحاوية |
| 2 | أوامر بسيطة لا تحتاج MTProto | اختبار تكامل لكل أمر وحفظ markup | إعادة توجيه الأمر إلى المعالج القديم |
| 3 | إعدادات المستخدم وMini App | عقد payload متطابق وقياسات أخطاء | إبقاء API وطبقة البيانات كما هي |
| 4 | الإشعارات والجدولة | عدم تكرار تسليم outbox في بيئة اختبار | تشغيل scheduler القديم على مثيل واحد فقط |
| 5 | البث الصوتي | بديل مثبت لـPyTgCalls أو عامل بث معزول | عزل البث عن نقل Bot API وعدم إيقافه أثناء النقل |

## قواعد التنفيذ

بدأت المرحلة الثانية بإصدار `aiogram` مقيد، وadapter injection في `build_dependencies`، وRouter فعلي لأوامر `/start` و`/help` و`about` و`back_to_start`. ابقِ Pyrogram والبث تحت مراقبة منفصلة إلى أن يثبت بديل البث، لأن Bot API وحده لا يؤدي مهام MTProto أو محادثات الصوت.

## تشغيل تجريبي قابل للتراجع

القيمة الافتراضية هي `TELEGRAM_RUNTIME=pyrogram` وتبقي جميع المسارات الحالية. يمكن تشغيل pilot محدود باستخدام `TELEGRAM_RUNTIME=aiogram`، ويشغّل عندها أوامر القائمة الثابتة فقط مع scheduler والإشعارات النصية، ويستبدل مدير البث ببديل صامت. لا تضبط `STREAM_ENABLED=true` معه؛ يرفض الإقلاع عمدًا كي لا يختفي بث صوتي من دون ملاحظة.

لا تشغّل runtimeين بالـbot token نفسه: سيحاول كلاهما long polling وسيتعارضان على التحديثات. التراجع هو إعادة `TELEGRAM_RUNTIME=pyrogram` ثم إعادة تشغيل الخدمة. لا يصبح aiogram الافتراضي قبل نقل الأوامر التفاعلية والإعدادات وتوفير بديل مناسب للبث.

> لا تتوقف خدمة البوت أو scheduler من أجل إعادة كتابة شاملة؛ النقل الصحيح يغيّر حدود الاعتماد، ثم يحول المسارات واحدًا واحدًا.
